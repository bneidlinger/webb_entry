[ 01 ] MISSION CONTEXT // what webbwatch even is

Every few hours, a new image or spectrum from the James Webb Space Telescope becomes public on the Mikulski Archive for Space Telescopes (MAST). Most of it is technical data with cryptic filenames (jw01193-c1034_t001_nircam_f444w-maskrnd-sub320a430r_psfstack.fits) buried behind a search portal designed for working astronomers. It is a treasure house with no signage.

WebbWatch AI exists to make that treasure house feel like a live feed: 

  ┌────────────────────────────────────────────────────────────────┐
  │  "new Webb data just dropped"                                  │
  │  "here is what instrument / filter / product type it is"       │
  │  "here is a preview image or spectrum"                         │
  │  "here is a first-pass AI + science-tool analysis"             │
  │  "here is why it might be interesting"                         │
  │  "here is the exact file, source archive, citation path"       │
  └────────────────────────────────────────────────────────────────┘

The plan is staged across eight phases (see webbwatch_ai_project_plan.md). Phase 0 stood up the skeleton. Phase 1 is what we just finished: the first real JWST data flowing in from MAST, into our database, out through our API, and onto a webpage. Everything else — previews, deterministic analysis, local AI, cloud AI, alerts, social feed — sits on top of this layer.

[ PRINCIPLE ] Deterministic tools first. AI second. The plan is explicit: AI never touches a file before boring, reproducible code has measured it. AI commentary is meaningless if the underlying pipeline is hallucinating filenames.

[ 02 ] THE PHASE 0 → 1 HANDOFF // skeleton to skin

Phase 0 left us with a working dial tone:

  • Monorepo: apps/web, services/api, services/worker, packages/shared, infra/, docs/.
  • Next.js 15 frontend that pings /health and shows an "API OK" badge.
  • FastAPI service with the /health route and a CORS config that lets the frontend talk to it.
  • RQ worker skeleton (process boots, attaches to Redis, listens on three queues — but no jobs registered yet).
  • Azurite + Postgres + Redis declared in docker-compose.yml (idle until Docker Desktop is installed).
  • A CloudAIProvider Protocol with two adapters (OpenAI + Azure OpenAI) and a factory that switches on AI_PROVIDER.
  • GitHub Actions CI: ruff + pytest + npm typecheck + next build.

But there was no actual data. The home page said "no products yet, run the CLI." There was no DB. There was no CLI. The api had exactly one endpoint and it returned the current time.

Phase 1 is the moment WebbWatch stops being a coathanger and starts having a torso. The deliverable from the plan: 

  ┌──────────────────────────────────────────────────────────┐
  │  Deliverable: App displays real JWST observations /      │
  │  products from MAST.                                     │
  └──────────────────────────────────────────────────────────┘

Five things we had to build for that one sentence to be true:

  1. A database with a schema for observations and products.
  2. A MAST client that can query the archive and return clean data.
  3. An ingest service that loads data into the database without creating duplicates.
  4. A CLI to run the ingest by hand.
  5. An API + frontend page that surface what got ingested.

[ 03 ] DATABASE LAYER // sqlalchemy + alembic, deeply

// why a database at all?

We could have made the frontend hit MAST directly on every page load. We did not. Four reasons:

  • Speed: MAST queries take 30-90 seconds. Nobody waits 60 seconds for a webpage.
  • Search: MAST's query API is rigid. SQL lets us slice by anything we choose to index.
  • Dedup & change detection: To say "this product is new" or "this got reprocessed" we have to remember what we saw last time.
  • Time series: Phase 7's "newly public" feed needs first_seen_at on every row. You only get that by writing it down.

// the models, in detail

Two tables. Plan §8 lists ~10 future tables, but Phase 1 only needs these two: 

# services/api/app/models/observation.py
class Observation(Base, TimestampMixin):
    __tablename__ = "observations"
    __table_args__ = (UniqueConstraint("mast_obs_id", name="uq_observations_mast_obs_id"),)

    id: Mapped[int] = mapped_column(primary_key=True)
    mast_obs_id: Mapped[str] = mapped_column(String(64), index=True, nullable=False)

    program_id:           Mapped[str | None] = mapped_column(String(32),  index=True)
    target_name:          Mapped[str | None] = mapped_column(String(256), index=True)
    instrument:           Mapped[str | None] = mapped_column(String(64),  index=True)
    filters:              Mapped[str | None] = mapped_column(String(256))
    ra:                   Mapped[float | None] = mapped_column(Float)
    dec:                  Mapped[float | None] = mapped_column(Float)
    observation_date:     Mapped[datetime | None] = mapped_column(DateTime(timezone=True))
    public_release_date:  Mapped[datetime | None] = mapped_column(DateTime(timezone=True))

    data_products: Mapped[list[DataProduct]] = relationship(...)

This is SQLAlchemy 2.0 typed declarative syntax. Worth knowing what each piece is:

  • Mapped[X] — a type hint that tells SQLAlchemy "this attribute is a column of type X." At runtime, instances of Observation have actual values; at type-check time, your IDE knows obs.ra is float | None.
  • mapped_column(...) — the actual column descriptor. Replaces the older Column() from SQLAlchemy 1.x.
  • UniqueConstraint("mast_obs_id") — this is the dedup contract at the database level. If two ingest runs race and both try to insert the same MAST observation, the database will reject one. We do NOT rely solely on application code to prevent dupes.
  • index=True — for fields we'll filter on (instrument, program_id, target_name) so the WHERE clauses don't full-table-scan.
  • relationship(...) — sets up the parent→children link so obs.data_products works in Python without us writing JOINs by hand.

DataProduct is the mirror table with a unique constraint on (observation_id, filename) — one row per file, no matter how many times MAST hands the same file back to us under different URIs.

// alembic: migrations are not optional

A migration is a file that records a change to the schema. Not a script that recreates the schema from scratch — a diff: "add column X," "rename table Y," "drop index Z." Migrations are the closest thing to git for databases.

Two reasons to use them from day one, not "later":

  • Two environments diverge instantly. Local dev is on SQLite. Prod will be on Azure Postgres. Without migrations, you can't reproducibly evolve both.
  • A migration in git is a record of intent. Code review the schema change at the same time as the code that needs it.

The flow:

$ python -m alembic revision --autogenerate -m "create observations and data_products"
INFO  [alembic.autogenerate.compare.tables] Detected added table 'observations'
INFO  [alembic.autogenerate.compare.tables] Detected added table 'data_products'
Generating alembic/versions/0f6caa2f9bf7_create_observations_and_data_products.py

$ python -m alembic upgrade head
INFO  [alembic.runtime.migration] Running upgrade  -> 0f6caa2f9bf7

Autogenerate compares the live database against your ORM models and writes the migration for you. It is smart but not infallible — always read the generated file before committing it. Alembic misses things like CHECK constraints, server defaults, and column reorderings.

Our alembic/env.py does one important non-default thing:

# Inject the runtime DATABASE_URL so alembic.ini doesn't need it hardcoded.
config.set_main_option("sqlalchemy.url", get_settings().database_url)

This means Alembic reads the same DATABASE_URL the app does. One environment variable controls "where am I writing." On a developer laptop it points at SQLite; in Azure Container Apps it will point at the managed Postgres instance.

[ DEEP CUT ] SQLite cannot ALTER TABLE DROP COLUMN (until very recent versions). Alembic gets around this with render_as_batch=True — it generates a "copy table to new schema, swap" dance. Our env.py turns this on automatically when the dialect is SQLite. You will hit this the first time you remove a column locally. Now you know why.

// sessions, two flavors

app/db.py exposes two ways to get a database session: 

def get_session() -> Iterator[Session]:
    """FastAPI dependency. Yields a session, commits on success, rolls back on error."""
    ...

@contextmanager
def session_scope() -> Iterator[Session]:
    """Plain context manager for CLI, scripts, tests."""
    ...

Same engine, same sessionmaker, two interfaces. The FastAPI side needs a dependency-injection-friendly generator. The CLI side needs a plain with block. Don't write both yourself in twenty places — write the helpers once.

[ 04 ] THE MAST CLIENT // taming astroquery

// what is MAST

Mikulski Archive for Space Telescopes, run by STScI in Baltimore. It is the canonical home of JWST data, plus Hubble, Kepler, TESS, and others. Its query interface is a thin layer over an internal database; you ask for observations matching criteria, then ask for the per-observation file list.

astroquery is the Python community's toolkit for astronomy archives. astroquery.mast.Observations is the JWST-flavored entrypoint: 

from astroquery.mast import Observations

obs_table = Observations.query_criteria(
    obs_collection="JWST",
    instrument_name="NIRCAM*",   # MAST stores as "NIRCAM/IMAGE", etc.
)
prod_table = Observations.get_product_list(obs_table)

Both calls return astropy.table.Table objects — fancy 2D arrays with named columns. Working with them directly is doable, but:

  • They carry numpy dtypes that don't map cleanly to SQLAlchemy.
  • Masked values are numpy.ma.masked, not None.
  • You can't pickle them; you can't easily mock them.

// why wrap astroquery

Our MastClient is the only place in the codebase that knows about astroquery. Everything downstream sees plain Python dataclasses: 

@dataclass
class MastObservation:
    mast_obs_id: str
    program_id:  str | None
    target_name: str | None
    instrument:  str | None
    filters:     str | None
    ra:          float | None
    dec:         float | None
    observation_date:    datetime | None
    public_release_date: datetime | None
    products: list[MastProduct] = field(default_factory=list)

Why this matters: our tests never touch the network. We construct synthetic astropy.table.Table objects in tests/test_mast_assemble.py, hand them to MastClient.assemble(...), and assert on the resulting dataclasses. Fast, deterministic, and resilient to MAST being down at midnight on a Saturday.

// the classification regex

JWST filenames encode their product type. The plan §4 lists ten product types worth caring about. We recognize them with a single regex: 

_PRODUCT_SUFFIX_RE = re.compile(
    r"_(?P<ptype>uncal|rate|rateints|cal|calints|i2d|s2d|s3d|x1d|c1d|cat|segm|phot|preview)"
    r"\.(?P<ext>fits|jpg|png|pdf|csv|ecsv)(?:\.gz)?$",
    re.IGNORECASE,
)

A cheat sheet for the four MVP product types:

i2dResampled 2D image. The pretty pictures.
x1dExtracted 1D spectrum (one source, flux vs wavelength).
c1dCombined 1D spectrum (multiple x1d stacks).
s2d2D spectral image (before extraction to 1D).

The Phase 3 preview generator will be product-type-aware: i2d gets an image preview with stretch options, x1d/c1d get a matplotlib flux-vs-wavelength chart. The regex is small but it gates that whole downstream behavior.

// MJD → datetime

MAST records times in Modified Julian Date (MJD) — days since November 17, 1858. Why 1858? Astronomical inside joke. We convert at the boundary: 

def _mjd_to_datetime(mjd: float | None) -> datetime | None:
    if mjd is None:
        return None
    try:
        return Time(mjd, format="mjd", scale="utc").to_datetime(timezone=UTC)
    except Exception:
        return None

Once it leaves the client, nobody downstream needs to know what an MJD is.

[ 05 ] INGEST SERVICE // idempotency as a discipline

// the property we want

  ┌──────────────────────────────────────────────────────────────┐
  │  Running ingest twice produces the same DB state as          │
  │  running ingest once. Running it a thousand times is fine.   │
  └──────────────────────────────────────────────────────────────┘

This is idempotency. Without it, every scheduled run would duplicate data, every retry on transient network failure would corrupt the database, and you could never re-run an ingest to "freshen" timestamps without fearing a side effect.

The signature:

def ingest_observations(session: Session, observations: Iterable[MastObservation]) -> IngestResult:
    ...

The algorithm, per observation:

  ┌─ for each MastObservation ──────────────────────────────┐
  │                                                         │
  │   query DB: SELECT * FROM observations                  │
  │             WHERE mast_obs_id = obs.mast_obs_id         │
  │                                                         │
  │   ┌─ exists? ──────────────────────────────────────┐    │
  │   │                                                │    │
  │   │   YES  → for each mutable field:               │    │
  │   │           if (incoming != stored): update      │    │
  │   │         count: observations_updated++          │    │
  │   │                                                │    │
  │   │   NO   → INSERT row; flush so we get obs.id    │    │
  │   │         count: observations_created++          │    │
  │   └────────────────────────────────────────────────┘    │
  │                                                         │
  │   ┌─ for each product of this observation ─────────┐    │
  │   │                                                │    │
  │   │   query DB: SELECT * FROM data_products        │    │
  │   │             WHERE observation_id = obs.id      │    │
  │   │               AND filename = prod.filename     │    │
  │   │                                                │    │
  │   │   exists? → maybe update + last_seen_at = now  │    │
  │   │   else   → INSERT + first_seen_at = now        │    │
  │   └────────────────────────────────────────────────┘    │
  └─────────────────────────────────────────────────────────┘

// first_seen vs last_seen

Two timestamps that look redundant aren't. first_seen_at is what we set on initial INSERT and never touch again. last_seen_at is bumped on every re-ingest. Why this matters:

  • Phase 2 alerts: a watchlist for "newly public products" fires when first_seen_at is recent — even if MAST has been quiet for hours and we've polled twenty times.
  • Phase 2 reprocessed-product detection: if last_seen_at stops advancing for a product, MAST has dropped it (probably replaced by a newer calibration).
  • Freshness metrics: "what's the oldest last_seen_at?" tells us if our poller is alive.

// the in-batch dedup bug

Our first version of the ingest loop had a subtle bug. The DB has a unique constraint on (observation_id, filename). We check it with session.scalar(SELECT ...) before inserting. Looks safe. Run the test that adds two products with the same filename in one batch: 

sqlalchemy.exc.IntegrityError: UNIQUE constraint failed:
  data_products.observation_id, data_products.filename

What happened: session.add(prod1) puts prod1 in the unit of work but does not yet flush to the DB. session.scalar(...) for prod2's duplicate-check queries the DB — which doesn't see prod1 yet — so the check passes. Both get added. The UNIQUE constraint fires at commit time.

The fix: track seen filenames in a Python set within the batch:

seen_filenames_this_batch: set[str] = set()
for src_prod in src_obs.products:
    if src_prod.filename in seen_filenames_this_batch:
        continue
    # ... normal path ...
    seen_filenames_this_batch.add(src_prod.filename)

This is belt-and-suspenders defense: the DB constraint is the absolute backstop, the Python guard is the performance and clarity layer. Both should exist.

// IngestResult: telemetry, not just logging

@dataclass
class IngestResult:
    observations_seen:    int = 0
    observations_created: int = 0
    observations_updated: int = 0
    products_seen:        int = 0
    products_created:     int = 0
    products_updated:     int = 0
    errors:               list[str] = field(default_factory=list)

Returning a structured result instead of logging strings means the CLI can render a Rich table, the API can return JSON, and Phase 2's scheduled worker can emit Prometheus-ready metrics. Same data, three surfaces. The function does not get to decide where its result is rendered.

[ 06 ] CLI // python -m app and why it matters

// the python -m pattern

The plan literally specified the command: 

$ python -m app ingest mast --instrument NIRCAM --limit 100

python -m app means "find the package named app, run its __main__.py." Why this instead of python app/cli.py or an entry-point script?

  • Package context. Imports work as from app.foo import bar, not from foo import bar. Avoids import-path confusion.
  • No setup.py shim. Works the moment you install the package (pip install -e .) with no entry-point boilerplate.
  • Composable. python -m app.cli.ingest would also work if we wanted to skip the top-level dispatcher.

// typer over click over argparse

Typer is built on Click. Click is built on argparse. Why typer? Function signatures become the CLI: 

@app.command("mast")
def ingest_mast(
    instrument:  str | None = typer.Option(None, "--instrument", "-i"),
    program_id:  str | None = typer.Option(None, "--program-id", "-p"),
    target_name: str | None = typer.Option(None, "--target", "-t"),
    limit: int = typer.Option(100, "--limit", "-n", min=1, max=10_000),
    dry_run: bool = typer.Option(False, "--dry-run"),
    json_output: bool = typer.Option(False, "--json"),
) -> None:
    ...

Type annotations on the parameters drive the CLI parser, validation, and the --help output. No separate schema to keep in sync. int means "must parse as an integer," the min=1, max=10_000 enforces the range with a friendly error.

// the two output modes

Default mode: rich.console.Console + rich.table.Table — pretty boxed output for humans. --json mode: a single JSON line on stdout — machine-readable for scripts, CI, and the eventual Phase 2 scheduled worker that will reuse the same code path.

[ WAR STORY ] Our first version printed f" → {n} observations" with a Unicode arrow. Worked fine in our editor. Failed instantly on PowerShell because Windows defaulted to cp1252 encoding for stdout. Lesson: in CLI output strings, prefer ASCII or set PYTHONIOENCODING=utf-8. Rich's box-drawing chars work because Rich talks to the Windows console API directly; our literal f-string did not.

// the endpoints

// from_attributes

Pydantic v2 schemas that read directly from SQLAlchemy objects use model_config = ConfigDict(from_attributes=True): 

class ObservationRead(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: int
    mast_obs_id: str
    program_id:  str | None
    target_name: str | None
    # ... etc

Then ObservationRead.model_validate(obs) pulls fields off the ORM object by attribute name. No manual { "id": obs.id, "mast_obs_id": obs.mast_obs_id ...} copy-paste.

// PEP 695 generics for pagination

class Page[T](BaseModel):
    items: list[T]
    total: int
    limit: int
    offset: int

That [T] on the class name is PEP 695 generic syntax, new in Python 3.12. Pre-3.12 you would write T = TypeVar("T"); class Page(BaseModel, Generic[T]):. The new syntax is cleaner. It is also why requires-python in our pyproject.toml is >=3.12.

Usage: Page[ObservationRead] and Page[ProductRow] are distinct response models with full type info. FastAPI uses these to generate the OpenAPI schema at /docs.

// flat product rows vs nested observation details

Notice we have ProductRow (a flat join of product + its parent observation) and ObservationDetail (an observation with its nested products list). These serve different UX needs:

  • Feed view wants a flat list — one row per file, each card needs target/instrument/program/filter without an extra fetch. → ProductRow.
  • Detail view wants "this one observation, with all its products." → ObservationDetail with selectinload to fetch products in a single extra query (avoids N+1).

// the admin sync endpoint

@router.post("/ingest/mast-sync")
async def mast_sync(...):
    client = MastClient()
    observations = await run_in_threadpool(client.fetch_jwst, ...)
    result = await run_in_threadpool(ingest_observations, session, observations)
    return IngestSyncResponse(**result.as_dict())

Two things to notice:

  • run_in_threadpool: astroquery is synchronous and slow. Calling it directly from an async def handler would block FastAPI's event loop for the entire 60-second MAST query. run_in_threadpool offloads to a worker thread.
  • This is a Phase 2 staging post. In Phase 2 the work moves to RQ — the endpoint will enqueue a job ID instead of blocking the request for a minute. For Phase 1, blocking the admin caller is acceptable.

[ 08 ] FRONTEND // Server Components, ISR, no client fetch

// the architectural choice

Look at components/product-feed.tsx: 

export async function ProductFeed() {
  const result = await getProducts({ limit: 50 });
  if (!result.ok) return <ErrorState ... />;
  if (result.data.items.length === 0) return <EmptyState />;
  return <table>...</table>;
}

That async function is a React Server Component. It runs on the Next.js server at request time, fetches from our FastAPI, and ships the rendered HTML to the browser. No JavaScript downloaded for the fetch. No client-side useEffect. No loading spinner. The user gets HTML.

This is the right call here because:

  • The data is the same for every visitor (no per-user filtering yet).
  • The feed updates seconds-to-minutes, not milliseconds — no need for client-side reactivity.
  • SEO and shareability: server-rendered HTML means a tweet preview, a social card, a screenshot all look right.

// ISR-style caching at the fetch level

fetch(`${API_BASE}/api/products?...`, {
  // The feed updates from background ingestion;
  // 10s is a reasonable freshness target.
  next: { revalidate: 10 },
});

next: { revalidate: 10 } tells Next.js: cache this response for 10 seconds, then revalidate on the next request. Result: 99% of page loads serve from cache, 1% trigger a background refresh, no user ever waits.

When you swap the data source later (replace SQLite with Azure Postgres, add Redis between API and DB), the frontend doesn't change. The contract is the JSON shape, not the storage.

[ 10 ] DECISIONS LOG // the choices behind the code

Decisions made in Phase 1 that future-you should not re-litigate without good reason:

SQLite local / Postgres prod One DATABASE_URL switch, zero per-dialect branches in models. Works because we stayed inside the SQLAlchemy-portable subset (no JSONB, no SQL functions, no Postgres-only types).
Wrap astroquery, don't expose it Tests never touch the network. Replacing astroquery later (with a custom MAST REST client, or astropy-only) is a contained refactor.
Sync DB sessions, not async The dominant workload is batch ingestion. Async SQLAlchemy adds complexity (separate engine class, await everywhere) for marginal benefit at our request volume. Revisit when the API gets popular.
Plain SQLAlchemy + separate Pydantic SQLModel merges them and is convenient for small projects, but has sharp edges around relationships and migrations. Standard SQLAlchemy + Pydantic v2 is more idiomatic and gives independent evolution.
Typer for CLI Type-annotation-driven CLIs are 1/3 the code of equivalent Click and play well with mypy.
Per-file ruff ignores (not global) Forces an intentional escape hatch. B008 ignored in routes (FastAPI Depends is idiomatic there) but enforced everywhere else.
Min Python 3.12 Enables PEP 695 generics (class Page[T]). Python 3.11 EOL is Oct 2027; cutting it now costs nothing.
Server Components, not client fetch The feed is shared, slow-moving, and benefits from server-side caching. Client-side fetching would add a loading spinner and SEO would be empty.
In-app dedup AND DB unique constraint Belt and suspenders. The DB constraint is the absolute backstop; the Python guard handles the in-batch case before it ever reaches the DB.

[ 11 ] GOTCHAS // bugs and surprises we cleared

// 1. GitHub push protection blocked the first commit

The Azurite emulator uses a well-known dev account key published in Microsoft's own docs. We put it in .env.example. GitHub's secret scanner doesn't know it's a published-by-Microsoft fake — it matched the pattern Azure Storage Account Access Key and rejected the push.

Fix: replace the literal key with the UseDevelopmentStorage=true SDK shortcut (Azure clients recognize it and fill in the dev account internally). Then squash the local history into a fresh root commit so the bad key never enters published git history.

// 2. Unicode arrow in CLI breaking on PowerShell

Covered in §06. PowerShell on Windows defaults to cp1252 for stdout encoding. Our CLI's f" → ..." crashed with UnicodeEncodeError.

Fix: ASCII in CLI literal strings, and set PYTHONIOENCODING=utf-8 for safety on Windows.

// 3. The in-batch dedup IntegrityError

Covered in §05. Two products with the same filename in one batch bypassed our SELECT-based duplicate check because the first INSERT was not yet flushed when the second check ran.

Fix: in-memory set of filenames seen this batch.

// 4. astroquery hanging on a second consecutive call

The first python -m app ingest mast completed cleanly. A second call from a fresh process never returned — suspect astroquery's local response cache holding a lock from the first process.

Workaround for now: verify dedup in-process with the live SQLite DB instead of round-tripping MAST twice. The actual fix is to disable or relocate the astroquery cache; a Phase 2 task because the scheduled poller will be running repeatedly from the same worker process.

[ 13 ] PHASE 2 PREVIEW // what we wire next

Phase 1 is the moment WebbWatch has a torso. Phase 2 is when it starts noticing things.

// the additions

  • Worker actually works. RQ jobs scheduled on a cron-like cadence (every 15 min: poll MAST; hourly: list S3 anonymously) calling the same ingest_observations we just wrote.
  • Watchlists. New ORM model with a criteria_json column. Users register interest in instruments, programs, targets, product types, sky regions, or keywords.
  • Matching engine. When a product is newly created (not just updated), evaluate every enabled watchlist against it. Emit alerts on matches.
  • Alerts table + UI. A /alerts page surfacing what fired and why.
  • Delivery adapters. At minimum a Discord webhook. Probably also Azure Communication Services email (more Azure practice). RSS feed for the patient.
  • Cross-cloud SNS bridge. AWS SNS topic for new JWST data can POST to an HTTPS endpoint hosted on Azure Container Apps — no AWS account needed on our side, just a verified subscription handshake at POST /api/webhooks/aws/jwst.

// the architectural pivot

The big shift: ingest stops being driven by humans running CLIs. The CLI stays as a developer tool, but the production path is RQ jobs scheduled by the worker. The API gains a job-status endpoint so the admin can see "last successful MAST poll: 3 minutes ago, 4 new products."

  • Move the ingest service into packages/shared/, or have the worker pip install -e ../api for now?
